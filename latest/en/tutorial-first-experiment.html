Tutorial: your first controlled experiment#

Quickstart ran one training once. A real experiment compares configurations under identical conditions and reads the results back. In this tutorial you will compare three algorithms at two sampling ratios, then dissect what “communication cost” actually means in fl-sim.

Everything runs on FedSynthetic — no downloads, seconds per run. The full script shown below lives at test-files/tutorial_first_experiment.py and is exercised in CI.

Prerequisites: Quickstart (the three-object model: dataset, model, server) and Core concepts (what a round does).

Set up the comparison#

Six runs: FedAvg (plain averaging), FedProx (proximal-regularized local objectives) and SCAFFOLD (control variates) — the classic gradient, proximal and variance-reduction axes — each at sampling ratios 0.5 and 1.0.

One deliberate choice: the dataset is constructed once, before any config or server. Config constructors re-seed the global RNG as they are built, so whatever was constructed last would otherwise shift the sampling stream of everything after it. The order dataset → config → server keeps every run reproducible:

import json
from pathlib import Path

import pandas as pd

from fl_sim.algorithms.fedopt import FedAvgClientConfig, FedAvgServer, FedAvgServerConfig
from fl_sim.algorithms.fedpd import FedPDClientConfig, FedPDServer, FedPDServerConfig
from fl_sim.algorithms.fedprox import FedProxClientConfig, FedProxServer, FedProxServerConfig
from fl_sim.algorithms.scaffold import SCAFFOLDClientConfig, SCAFFOLDServer, SCAFFOLDServerConfig
from fl_sim.data_processing.fed_synthetic import FedSynthetic

ALGORITHMS = {
    "FedAvg": (FedAvgServer, FedAvgServerConfig, FedAvgClientConfig),
    "FedProx": (FedProxServer, FedProxServerConfig, FedProxClientConfig),
    "SCAFFOLD": (SCAFFOLDServer, SCAFFOLDServerConfig, SCAFFOLDClientConfig),
    "FedPD": (FedPDServer, FedPDServerConfig, FedPDClientConfig),
}

# SCAFFOLD's server config requires its global step size, and FedPD's
# upload frequency is 0 < p < 1 (it uploads once every int(1/p) rounds);
# the others use their defaults.
SERVER_KW = {"FedAvg": {}, "FedProx": {}, "SCAFFOLD": {"lr": 0.03}, "FedPD": {"p": 0.3}}

# one synthetic dataset, split across 30 clients, shared by every run below
dataset = FedSynthetic(1.0, 1.0, True, 30)


def run(algorithm, sample_ratio, num_iters, tag, **extra_kw):
    """Train one algorithm and return the server.

    Every run takes a FRESH model from ``dataset.candidate_models``
    (a property building a new module on each access): the server trains
    the model it is given in place, so sharing one model across runs
    would warm-start every run after the first and contaminate the
    comparison. Algorithm-specific server keywords (SCAFFOLD's global
    step size, FedPD's upload frequency ``p``) come from ``SERVER_KW``;
    anything passed as ``extra_kw`` is merged on top.
    """
    server_cls, server_config_cls, client_config_cls = ALGORITHMS[algorithm]
    server_kw = {**SERVER_KW[algorithm], **extra_kw}
    server = server_cls(
        dataset.candidate_models["mlp_d1"],
        dataset,
        server_config_cls(
            num_iters=num_iters,
            num_clients=30,
            clients_sample_ratio=sample_ratio,
            log_dir=f"t1_{tag}",
            **server_kw,
        ),
        client_config_cls(batch_size=32, num_epochs=1),
    )
    server.train()
    return server


def final_accuracy(server):
    """Read the last logged server-side validation accuracy of a run.

    The JSON logger buffers in memory; flush it to materialize the file.
    """
    server._logger_manager.flush()
    log_dir = Path(server._logger_manager.log_dir)
    metrics_file = next(p for p in log_dir.glob("*.json") if p.name != "config.json")
    metrics = json.loads(metrics_file.read_text())
    return metrics["val"]["Server"][-1]["acc"]

final_accuracy reads a run’s JSON log — the same file format you saw in Quickstart. SCAFFOLD needs its global step size lr passed explicitly (its config has no default for it); FedPD will need a frequency parameter later. Both are per-algorithm server keywords, collected in SERVER_KW.

Run and read the results#

The comparison itself is a loop, and the results land in a pandas.DataFrame:

results = []
for algorithm in ("FedAvg", "FedProx", "SCAFFOLD"):
    for sample_ratio in (0.5, 1.0):
        server = run(algorithm, sample_ratio, num_iters=3, tag=f"{algorithm}_{sample_ratio}")
        results.append(
            {
                "algorithm": algorithm,
                "sample_ratio": sample_ratio,
                "num_communications": server._num_communications,
                "final_acc": round(final_accuracy(server), 4),
            }
        )

print(pd.DataFrame(results).to_string(index=False))

Output on one machine (your numbers may differ slightly by package version):

algorithm  sample_ratio  num_communications  final_acc
   FedAvg           0.5                  90     0.8114
   FedAvg           1.0                 180     0.8767
  FedProx           0.5                  90     0.8776
  FedProx           1.0                 180     0.8776
 SCAFFOLD           0.5                  90     0.8767
 SCAFFOLD           1.0                 180     0.8767

Two honest observations about this table:

  • This synthetic task is easy — FedProx and SCAFFOLD reach the same accuracy ceiling as FedAvg at full sampling. Their advantages show up on harder, more heterogeneous tasks (see the algorithm theory pages for when each helps).

  • The accuracy story saturates; the communication story does not. Every run at ratio 0.5 used exactly 90 communications and every run at ratio 1.0 used exactly 180 — regardless of the algorithm. That number deserves a closer look, because it is easy to misread.

What num_communications counts#

num_communications counts messages, not rounds: each round adds one downlink broadcast per sampled client plus one uplink reply per sampled client. With 30 clients at ratio 0.5, every round is 15 downlinks + 15 uplinks = 30 messages, so 3 rounds = 90; at ratio 1.0 that doubles to 180.

The discriminating check: 3 rounds at full sampling and 6 rounds at half sampling both land on 180. The counter scales with 2 × sampled_clients × rounds, not with rounds. Reading it as “communication rounds” would make 90 look like “90 rounds” — off by a factor of 30.

The decomposition to keep in mind:

\[\text{FedAvg} = 2 \times \text{sampled} \times \text{rounds}\]

(Note also that the step recorded in the JSON log is a snapshot taken at the start of each round: it trails the final counter by the last round’s full cost — read the final count from the server, as the scripts here do.)

Sampling is not communicating#

All three algorithms above communicate every round. fl-sim also ships communication-skipping algorithms, and they break the 2 × sampled × rounds identity in an instructive way. Run FedPD — which uploads only every int(1/p)-th round — for five rounds next to a five-round FedAvg:

fedavg = run("FedAvg", 0.5, num_iters=5, tag="FedAvg_5it")
fedpd = run("FedPD", 0.5, num_iters=5, tag="FedPD_5it")

# The skipped rounds emit expected RuntimeWarnings on both the server
# and the client side -- see the tutorial page for what they mean.
for name, server in [("FedAvg", fedavg), ("FedPD", fedpd)]:
    sampled = 15  # 30 clients x 0.5
    downlink = sampled * 5  # every round broadcasts to every sampled client
    uplink = server._num_communications - downlink
    print(
        f"{name}: {server._num_communications} communications = "
        f"{downlink} downlink + {uplink} uplink ({uplink // sampled} of 5 rounds uploaded)"
    )

Output on one machine:

FedAvg: 150 communications = 75 downlink + 75 uplink (5 of 5 rounds uploaded)
FedPD: 90 communications = 75 downlink + 15 uplink (1 of 5 rounds uploaded)

The decomposition says it precisely: the downlink is identical (75 = 5 rounds × 15 clients — broadcasting to the sampled set is never skipped); FedPD saves uplinks only. Five FedPD rounds cost the same 90 messages as three FedAvg rounds — the same communication budget buys two extra local iterations.

Three practical details when you run this yourself:

  • p must satisfy 0 < p < 1. With p = 1 FedPD uploads every round (degenerating to FedAvg); with p > 1 the upload frequency becomes zero and the run crashes. The config exposes p but the derived upload frequency int(1/p) always wins — passing a comm_freq yourself is silently overwritten.

  • You will see RuntimeWarnings — they are expected, not errors. The server logs No message received from the clients... once per skipped round (“nobody uploaded this round, so the global model did not move”), and each skipping client logs No parameters received from server... (“I was not given a new global model this round, so I keep working from my current parameters”). At tutorial scale the client-side message appears once per (skipped client × skipped round), so it dominates the console. Both are how FedPD is designed to behave.

  • The JSON step snapshot trails differently per algorithm: for the five-round FedAvg it ends at 120 (the last round’s 30 messages are unlogged), for FedPD at 75 (its last round never uploads). The final counts come from server._num_communications.
