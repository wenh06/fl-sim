Tutorial: parallel and reproducible runs#

Larger experiments take longer to train. fl-sim can execute the clients’ local steps concurrently on a thread pool — with a one-line config change — and this tutorial shows how to keep the run reproducible while doing so: at the end, two different backends produce bitwise identical final model weights.

The full script lives at test-files/tutorial_parallel_check.py and is exercised in CI. Prerequisites: Tutorial: your first controlled experiment.

The mechanics behind this are documented in Parallel execution layer (backends, guarantees, and how custom algorithms stay compatible); this page is the hands-on version.

Enabling parallel execution#

Add executor="threads" to the server config. Nothing else changes — algorithms, datasets, logging and the participation schedule all behave identically; only the per-client local steps (evaluate → local update → build upload) run on a thread pool:

import torch

from fl_sim.algorithms.fedopt import FedAvgClientConfig, FedAvgServer, FedAvgServerConfig
from fl_sim.data_processing.fed_synthetic import FedSynthetic

dataset = FedSynthetic(1.0, 1.0, True, 30)


def run(executor, tag, rng_mode):
    """One FedAvg run on the given executor backend."""
    return FedAvgServer(
        # a fresh model per run (see the first-experiment tutorial)
        dataset.candidate_models["mlp_d1"],
        dataset,
        FedAvgServerConfig(
            num_iters=3,
            num_clients=30,
            clients_sample_ratio=0.5,
            executor=executor,  # "sequential" (default) or "threads"
            num_workers=2,
            log_dir=f"t4_{tag}",
        ),
        FedAvgClientConfig(batch_size=32, num_epochs=1, rng_mode=rng_mode),
    )


def weights_of(server):
    return list(server.model.state_dict().values())


def bitwise_equal(a, b):
    return all(torch.equal(x, y) for x, y in zip(weights_of(a), weights_of(b)))

The helpers capture what we will compare: the final model weights (weights_of) and an exact equality check over them (bitwise_equal — torch.equal, not allclose).

The two backends produce identical results#

Run the same experiment on both backends with the client config’s rng_mode="per_client" — each client’s dataloaders get their own generators seeded from (seed, client_id, round) — and compare:

sequential = run("sequential", "seq", rng_mode="per_client")
threads = run("threads", "threads", rng_mode="per_client")

print(
    f"per-client RNG:  communications equal: "
    f"{sequential._num_communications == threads._num_communications}, "
    f"final weights bitwise equal: {bitwise_equal(sequential, threads)}"
)

Output:

per-client RNG:  communications equal: True, final weights bitwise equal: True

The results are bitwise identical — not merely close, but the same tensors. This holds regardless of how many workers ran or how the operating system scheduled them.

Behavior of the global RNG mode#

rng_mode defaults to "global": clients share the process-global torch RNG. The script runs the same comparison in that mode too:

sequential_g = run("sequential", "seq_global", rng_mode="global")
threads_g = run("threads", "threads_global", rng_mode="global")

# with the process-global RNG, the participation sets and the aggregation
# arithmetic stay identical, but the clients' local trajectories consume
# the shared RNG concurrently, so the final weights may differ — this is
# the documented (and expected) statistical-level behaviour
print(
    f"global RNG:      communications equal: "
    f"{sequential_g._num_communications == threads_g._num_communications}, "
    f"final weights bitwise equal: {bitwise_equal(sequential_g, threads_g)} (may be False by design)"
)

Under the global mode the participation schedule and the aggregation arithmetic are still backend-independent (sampling decisions and reply consumption happen on the main thread in fixed order), so the communication counts always match. The clients’ local trajectories, however, consume the shared RNG concurrently — so their interleaving depends on thread scheduling, and the final weights may differ between backends and between repeats:

global RNG:      communications equal: True, final weights bitwise equal: True (may be False by design)

(On a small run like this one, the tasks often serialize and even the weights may match; this is incidental rather than guaranteed.)

Practical guidance:

  • exploring: global mode is acceptable; run-to-run variation is part of the measurement (average over seeds, as in Tutorial: visualize and export results).

  • paper-grade seed alignment: either stay on "sequential", or set rng_mode="per_client" — then every backend, every parallelism degree and every repeat produce the same trajectory from the same seed.
