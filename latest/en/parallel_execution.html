Parallel execution layer#

Added in version 0.2.0.

fl-sim simulates all clients and the server inside one Python process. Historically the clients’ local training ran strictly sequentially; the parallel execution layer lets the per-client local steps (evaluate → local update → build the upload) run concurrently, on a pluggable executor backend, while every server-side state change stays on the main thread in the fixed sampled-client order.

Quick start#

Enable the thread-pool backend with two keyword arguments on the server config:

from fl_sim.algorithms.fedopt import FedAvgServerConfig

config = FedAvgServerConfig(
    num_iters=100,
    num_clients=200,
    clients_sample_ratio=0.1,
    executor="threads",   # default: "sequential" (exactly the pre-parallel behavior)
    num_workers=8,        # 0 = auto (usable CPU count, container-aware)
)

Nothing else changes: algorithms, datasets and logging behave identically; the clients’ local steps are simply dispatched to a thread pool. The backends are also selectable per experiment through the environment variables FL_SIM_EXECUTOR / FL_SIM_NUM_WORKERS (which override the config; used by CI to run the per-algorithm test functions under a parallel backend).

Backends#

Backend

Config value

Notes

Sequential

"sequential" (default)

Exactly the pre-parallel behavior, down to log ordering and exception timing.

Threads

"threads"

ThreadPoolExecutor-based. Client state needs no serialization (models and datasets stay put); PyTorch releases the GIL inside its compute kernels and CUDA calls, so the local-training workload parallelizes despite the GIL. The torch intra-op thread budget is automatically reduced to cores // num_workers while active and restored afterwards; torch_num_threads overrides this explicitly.

Measured speedups (best of 3 runs; see test-files/benchmark_executors.py and test-files/benchmark_gpu.py to reproduce; the committed benchmark_executors_results.data holds the CPU run):

  • CPU, tiny model (MLP, tens of ms per client task; 64 clients, 3 iterations): about 1.2× at 2–4 workers, degrading slightly beyond that as GIL contention dominates. The Python glue code (batch loops, optimizer stepping) holds the GIL most of the time on such workloads.

  • CPU, compute-heavier model (1.19M-parameter MLP, 5 local epochs, batch 256, 12-core host): 1.40× at 8 workers — the torch kernels release the GIL, so the benefit grows with the compute share of each client task.

  • single GPU: no benefit from the threads backend (sequential and threads measure the same within noise): all clients submit kernels to the same device, where they execute serially anyway — the sequential loop already keeps a single GPU fed. (The measured GPU run was itself ~3× faster than the CPU run for this workload.) Scaling beyond one GPU comes from multi-GPU client placement (ServerConfig.visiable_gpus) or CUDA streams, not from concurrent submission to one device.

These are observations on the measured configurations, not ceilings: the per-backend arithmetic guarantees (fixed aggregation order, identical participation sets) hold regardless of the achieved speedup, and the (planned) process-based backend targets the CPU workloads where the GIL bounds the threads backend.

How it works#

Each communication round runs as:

  1. Main thread — the uplink decision (per algorithm, e.g. FedPD’s stochastic participation) and the downlink broadcast;

  2. Executor — the per-client task evaluate → update → build_reply, which only ever touches its own client’s state;

  3. Main thread — the replies are consumed in the sampled-client order, then metrics aggregation and the global update.

Because step 3 always happens in a fixed order regardless of the backend, the floating-point aggregation arithmetic is identical across backends — only the clients’ local trajectories can interleave.

Reproducibility#

Three levels, spelled out explicitly:

Backend

What is guaranteed

sequential

The full run is bitwise identical to the pre-parallel implementation (same machine/version/seed), including communication counters and logs.

threads

The aggregation arithmetic is bitwise identical to sequential (fixed consumption order); the participation sets are identical (decisions are made on the main thread, serially); only the clients’ local trajectories may differ statistically from the sequential run (concurrent consumption of the process-global RNG).

any parallel backend

For paper-grade seed alignment, either use sequential, or set rng_mode="per_client" (below).

rng_mode="per_client"#

Added in version 0.2.0.

Setting rng_mode="per_client" on the client config re-arms every client’s train/val dataloaders with per-client torch.Generator`s seeded deterministically from ``(seed, client_id, round)`. The shuffle stream of each client is then bitwise identical across backends, parallelism degrees, and same-seed repeats — including the final model weights.

from fl_sim.algorithms.fedopt import FedAvgClientConfig

client_config = FedAvgClientConfig(32, 2, lr=0.01, rng_mode="per_client")

Scope: only the dataloader shuffling is isolated this way; dropout and other model-internal randomness still draw from the process-global torch RNG (isolating those would require functional-RNG rewrites; the practical recipe for bitwise comparisons remains sequential).

Writing custom algorithms#

A client algorithm hook that wants to be parallel-safe obeys one rule:

  • Client.communicate(self) builds and returns the ClientToServer message and never touches the server (the upload and the communication counter are handled by the framework);

  • legacy-style overrides communicate(self, target) (uploading through target themselves) still work on the sequential backend (with a DeprecationWarning) but are rejected on parallel backends, since reading server state from a worker task is impossible by construction.

All built-in algorithms follow the new contract; see test-files/custom_alg.py for a complete example.

Relation to the experiment-level multiprocessing#

fl_sim.utils.multiprocessing (and the Server._subprocess progress reporting) provides experiment-level parallelism: several experiment configs → several spawned processes. The executor layer provides client-level parallelism within one experiment. The two are orthogonal and can be combined; the progress reporting works unchanged under both.

API#

fl_sim.executors#

Pluggable client-executor backends for the parallel execution layer.

The executor maps a batch of per-client tasks onto execution resources while preserving the sampled order of the results; see ClientExecutor for the contract.

class fl_sim.executors.ClientExecutor[source]#

Bases: ABC

Maps a batch of client tasks onto execution resources.

Contract#

  • map() calls fn once per item and returns the results as a list whose order matches items (never completion order — the aggregation consumes the buffer in the sampled order, which is what makes the aggregation arithmetic backend-independent).

  • on_complete(result, index) is called on the main thread as soon as each task finishes, driving progress feedback; it must not mutate server aggregation state.

  • a task exception is re-raised with the failing client’s context (raise ... from exc); pending not-yet-started tasks are cancelled on a best-effort basis (already-running ones inevitably run to completion — a thread/process-pool physical fact, documented).

  • instances are context managers: entering saves and applies the execution resources (e.g. the intra-op thread budget), exiting restores the previous values.

class fl_sim.executors.SequentialExecutor[source]#

class fl_sim.executors.ThreadsExecutor(num_workers: int = 0, torch_num_threads: int | None = None)[source]#

Bases: ClientExecutor

Runs the client tasks on a thread pool, preserving the sampled order.

Parameters:

  • num_workers (int) – The maximum number of client tasks running concurrently; 0 means auto (the usable CPU count).

  • torch_num_threads (int, optional) – The intra-op thread budget to set while active; None means auto (usable cores // num_workers, at least 1). Passing an explicit value also disables the automatic budgeting.
