How to: implement a custom algorithm#

Built-in algorithms cover the classical methods; research often requires variants. This guide implements a complete algorithm — a FedProx variant with named parameter exchange and optional variance reduction — walking through every file you need and every hook you can override. The running example is test-files/custom_alg.py; the code shown below is included from that file, so it is exercised in CI (the CLI runs it via test-files/custom_conf.yml).

The one-sentence model: an algorithm is two config classes plus hook overrides on the Server and Client classes — the training loop, the communication schedule scaffolding, logging, evaluation and the parallel executors all stay untouched (Core concepts explains why).

When is a custom algorithm needed?#

  • your algorithm changes what clients compute locally (new local objective, extra local state) → override client hooks;

  • it changes what is exchanged or how replies are aggregated → override server hooks;

  • it needs new hyperparameters → add config fields.

If you only need different values for existing hyperparameters, no code is needed — use the built-in algorithm’s config.

The config classes#

Two pydantic models, one for each side. New fields become CLI/CLI-YAML options automatically; server_config_kw_doc / client_config_kw_doc append the inherited fields’ docs so the API reference stays complete:

@register_algorithm()
@add_docstring(server_config_kw_doc, "append")
class CustomServerConfig(ServerConfig):
    """Server config for the Custom algorithm.

    Parameters
    ----------
    num_iters : int
        The number of (outer) iterations.
    num_clients : int
        The number of clients.
    clients_sample_ratio : float
        The ratio of clients to sample for each iteration.
    vr : bool, default False
        Whether to use variance reduction.
    **kwargs : dict, optional
        Additional keyword arguments:
    """

    __name__ = "CustomServerConfig"

    vr: bool = False


@register_algorithm()
@add_docstring(client_config_kw_doc, "append")
class CustomClientConfig(ClientConfig):
    """Client config for the Custom algorithm.

    Parameters
    ----------
    batch_size : int
        The batch size.
    num_epochs : int
        The number of epochs.
    lr : float, default 1e-2
        The learning rate.
    mu : float, default 0.01
        Coefficient for the proximal term.
    vr : bool, default False
        Whether to use variance reduction.
    **kwargs : dict, optional
        Additional keyword arguments:
    """

    __name__ = "CustomClientConfig"

    lr: float = 1e-2
    mu: float = 0.01
    vr: bool = False
    # NOTE: the optimizer is fixed by the algorithm (derived from `vr`),
    # mirroring ``FedProxClientConfig``
    optimizer: str = ""

    @model_validator(mode="after")
    def _fix_optimizer(self) -> "CustomClientConfig":
        if "optimizer" in self.model_fields_set and self.optimizer:
            warnings.warn(
                "The `optimizer` argument is fixed to `FedProx` or `FedProx_VR` and will be ignored.",
                RuntimeWarning,
            )
        self.optimizer = "FedProx_VR" if self.vr else "FedProx"
        return self

The model_validator here fixes the local optimizer from the vr flag — config-level invariants belong in validators, so invalid combinations fail at construction, not mid-run.

The server hooks#

The server customizes the downlink (communicate) and the aggregation (update). Everything else — sampling, the round loop, metrics — is inherited:

@register_algorithm()
@add_docstring(
    Server.__doc__.replace(
        "The class to simulate the server node.",
        "Server node for the Custom algorithm.",
    )
    .replace("ServerConfig", "CustomServerConfig")
    .replace("ClientConfig", "CustomClientConfig")
)
class CustomServer(Server):
    """Server node for the Custom algorithm."""

    __name__ = "CustomServer"

    def _post_init(self) -> None:
        """
        check if all required field in the config are set,
        and check compatibility of server and client configs
        """
        super()._post_init()
        assert self.config.vr == self._client_config.vr

    @property
    def client_cls(self) -> type:
        return CustomClient

    def _named_params_state(self) -> Dict[str, torch.Tensor]:
        """Model parameters as a named mapping (the ModelState format, parameters only)."""
        return {n: p.detach().clone() for n, p in self.model.named_parameters()}

    def communicate(self, target: "CustomClient") -> None:
        # named exchange: broadcast the global model state by parameter names
        extras = {}
        if target.config.vr:
            extras["gradients"] = [
                p.grad.detach().clone() if p.grad is not None else torch.zeros_like(p) for p in target.model.parameters()
            ]
        target.receive(ServerToClient(model_state=self._named_params_state(), extras=extras))

    @torch.no_grad()
    def update(self) -> None:
        # average the received (named) model states into the global model, by name
        global_state = {n: torch.zeros_like(p) for n, p in self.model.named_parameters()}
        for m in self._received_messages:
            for n, v in m["model_state"].items():
                global_state[n] += v.detach().clone().to(self.device) / len(self._received_messages)
        for n, p in self.model.named_parameters():
            p.data.copy_(global_state[n].to(p.device))
        if self.config.vr:
            self.update_gradients()

    @property
    def config_cls(self) -> Dict[str, type]:
        return {
            "server": CustomServerConfig,
            "client": CustomClientConfig,
        }

    @property
    def doi(self) -> List[str]:
        return ["10.48550/ARXIV.1812.06127"]

Points worth noting:

  • communicate(target) builds a typed ServerToClient message; extras carries algorithm-specific payloads (here, server-side gradients for variance reduction) alongside the model.

  • update() runs on the main thread after the sampled clients’ replies arrive in self._received_messages — in sampled-client order, which is what keeps aggregation bitwise identical across Parallel execution layer backends.

  • client_cls and config_cls wire the custom classes together; @register_algorithm() (shown above each class) makes the algorithm usable by name.

The client hooks#

The client customizes the local training (update) and the uplink (communicate):

@register_algorithm()
@add_docstring(
    Client.__doc__.replace(
        "The class to simulate the client node.",
        "Client node for the Custom algorithm.",
    ).replace("ClientConfig", "CustomClientConfig")
)
class CustomClient(Client):
    """Client node for the Custom algorithm."""

    __name__ = "CustomClient"

    def _post_init(self) -> None:
        """
        check if all required field in the config are set,
        and set attributes for maintaining itermidiate states
        """
        super()._post_init()
        if self.config.vr:
            self._gradient_buffer = [torch.zeros_like(p) for p in self.model.parameters()]
        else:
            self._gradient_buffer = None

    def _named_params_state(self) -> Dict[str, torch.Tensor]:
        """Model parameters as a named mapping (the ModelState format, parameters only)."""
        return {n: p.detach().clone() for n, p in self.model.named_parameters()}

    def accept_parameters(self) -> None:
        """Load the received named state into the model, by name.

        The mapping carries parameters only, so the loading is done by name
        rather than via the default :meth:`set_model_state` (which expects
        a full module ``state_dict``, buffers included).
        """
        state = self._received_messages.get("model_state", None)
        if state is not None:
            for n, p in self.model.named_parameters():
                p.data.copy_(state[n].data.to(p.device))

    def communicate(self) -> ClientToServer:
        # named exchange: upload the local model state by parameter names.
        # New-style hook: build and RETURN the typed message; the upload and
        # the communication counter are handled by the framework (the hook
        # itself never touches the server, so it can run in a worker task).
        extras = {}
        if self.config.vr:
            extras["gradients"] = [p.grad.detach().clone() for p in self.model.parameters()]
        return ClientToServer(
            client_id=self.client_id,
            train_samples=len(self.train_loader.dataset),
            metrics=self._metrics,
            model_state=self._named_params_state(),
            extras=extras,
        )

    def update(self) -> None:
        try:
            state = self._received_messages["model_state"]
        except KeyError:
            warnings.warn(
                "No model state received from server. " "Using current model parameters as initial parameters.",
                RuntimeWarning,
            )
            state = self._named_params_state()
        # the (list-based) local solver reads the initial parameters positionally;
        # extract them from the received named state, by name
        self._cached_parameters = [state[n].to(self.device) for n, _ in self.model.named_parameters()]
        if self.config.vr and self._received_messages.get("gradients", None) is not None:
            self._gradient_buffer = [gd.clone().to(self.device) for gd in self._received_messages["gradients"]]
        self.solve_inner()  # alias of self.train()

    def train(self) -> None:
        self.model.train()
        with tqdm(
            range(self.config.num_epochs),
            total=self.config.num_epochs,
            mininterval=1.0,
            disable=self.config.verbose < 2,
            leave=False,
        ) as pbar:
            for epoch in pbar:  # local update
                self.model.train()
                for X, y in self.train_loader:
                    X, y = X.to(self.device), y.to(self.device)
                    self.optimizer.zero_grad()
                    output = self.model(X)
                    loss = self.criterion(output, y)
                    loss.backward()
                    self.optimizer.step(
                        local_weights=self._cached_parameters,
                        variance_buffer=self._gradient_buffer,
                    )
                    # free memory
                    del X, y, output, loss
        self.lr_scheduler.step()

The most important contract on this page is in communicate: it builds and returns a ClientToServer and touches nothing but the client’s own state. The framework sends the message and maintains the communication counters. That is what makes the hook safe to run inside a worker thread when parallel execution is on — a hook that reached into server state would only work sequentially.

Named exchange, by the way#

This example exchanges parameters by name (a model_state mapping from parameter name to tensor, i.e. ModelState) instead of the legacy flat positional list. Names survive reordering and partial modules, and the loading side (accept_parameters, update) looks parameters up by name. The flat-list style still works everywhere; prefer names for new algorithms.

Register and run#

@register_algorithm() (applied to all four classes above) puts the algorithm into the registry; from then on the CLI and YAML matrices accept it like any built-in:

algorithm:
  name: Custom
  server:
    num_iters: 100
    vr: true
  client:
    num_epochs: 5

The same four classes work programmatically, exactly like Quickstart:

server = CustomServer(
    model, dataset, CustomServerConfig(num_iters=5), CustomClientConfig(num_epochs=1)
)
server.train()

Safeguards for registered algorithms#

Two layers guard a registered algorithm:

  • the golden regression suite (test/test_parallel_equivalence/) pins each algorithm’s observable trajectory (messages, decisions, counters, metrics positions) so refactors cannot silently change behavior;

  • the hook contract test (test/test_hook_contract.py) asserts that client hooks touch no server state — the parallel-safety property communicate above was written for.

When you add an algorithm to the repository itself, add it to both.

Legacy hook style#

Older code overrides communicate(self, target) on the client and mutates server state directly. It still works under the sequential backend (with a DeprecationWarning), but it is incompatible with parallel backends and will be removed; new algorithms should build and return the typed message as shown above.
